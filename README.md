# KALMUS Web

## 1. Project Overview
**KALMUS Web** is a web-based application built around the [KALMUS Python package](https://pypi.org/project/kalmus/), a computational tool designed for the quantitative analysis and visualization of colors in films. 

This project extends the KALMUS command-line and GUI capabilities by providing a modern web interface to offload computationally heavy video processing tasks to High-Performance Computing (HPC) clusters via SLURM. Users can seamlessly upload movies, configure processing options, and retrieve rich, client-side visualizations (e.g., Hue histograms, RGB cubes, 3D bar charts, and color barcodes) directly from their browser.

---

## 2. Architecture & System Design
The system uses a decoupled architecture bridged by a shared NFS filesystem, utilizing a modern web stack for the frontend and a robust, scalable HPC environment for backend processing.

### **Tech Stack**
- **Frontend / API Gateway:** Next.js 16 (React 19, TypeScript), Tailwind CSS 4
- **Backend Processing:** Python 3.7/3.8, KALMUS Library
- **Task Scheduling:** SLURM Workload Manager
- **Visualizations:** Plotly.js (Client-side)
- **Storage:** Shared NFS Filesystem

### **System Components**
1. **Next.js Web Interface:** Handles user configuration, chunked parallel video uploads, and visualizes processed results.
2. **Next.js API Routes:** Acts as an orchestrator proxying requests, assembling file chunks, caching external metadata (OMDb), and generating/submitting SLURM batch scripts.
3. **SLURM Compute Nodes:** Receives the batch jobs and allocates resources (4 CPUs, 16GB RAM, 1hr limits per job) to run Python processing scripts (e.g., `command_line_generator.py` or equivalent kalmus processing).
4. **Shared NFS Storage:** Bridges the gap between the Next.js web server and the SLURM compute nodes by providing a unified storage location for video uploads and JSON/PNG outputs.

## 4. Data Flow
The process from video upload to final visualization follows this asynchronous workflow:

1. **Upload & Configuration:** The user selects a movie file and queries OMDb for metadata. For large files, the client performs chunked parallel uploading (4 concurrent requests, 5-25MB chunks) to the Next.js API.
2. **File Assembly & Orchestration:** The `/api/assemble-file` route stitches the chunks together on the web server's NFS mount. It caches the OMDb metadata in `metadata.json`.
3. **Job Submission:** The Next.js API generates a SLURM batch script (`sbatch`) and submits it to the cluster.
4. **HPC Processing:** A SLURM compute node picks up the job, running the KALMUS python pipeline on the video. It extracts frame colors, calculates histograms, and exports results.
5. **Output Delivery:** The compute node saves `barcode.png`, `barcode.json`, and `summary.json` to the job's directory in the shared NFS (`/shared/kalmus/results/[jobId]/`).
6. **Polling & Rendering:** The user's browser polls `/api/job-status/[jobId]`. Once successful, it fetches the output JSONs and renders interactive Plotly visualizations (Hue/Light scatter, RGB cubes, etc.).

## 5. Storage Schema & "Database"
Instead of a traditional SQL/NoSQL database, KALMUS Web relies on a **File-Based schema** stored on the shared NFS directory. Every job gets a unique identifier (`jobId`), and its state/data is maintained within a dedicated folder: `/shared/kalmus/results/[jobId]/`.

**Folder Structure per Job:**
- `video_input.mp4` *(Temporary)*: The assembled video file waiting to be processed.
- `metadata.json`: Captured at submission time. Contains standard OMDB information (`imdb_id`, `title`, `year`, `genre`, `poster_url`) and a `raw` field with the complete OMDb payload.
- `barcode.json`: The core output generated by the python backend. Contains arrays of RGB colors, brightness arrays, and frame-by-frame processing parameters.
- `summary.json`: High-level aggregated statistics of the video's color composition.
- `barcode.png`: The visually rendered timeline image of the color barcode.

## 6. API Reference
The Next.js backend provides the following internal API routes to facilitate the workflow.

### **File Upload & Job Management**
- `POST /api/generate-barcode`
  - Direct file upload for files `< 50MB`. Initiates the SLURM job instantly.
- `POST /api/upload-chunk`
  - Receives parts of large files.
  - **Payload:** `FormData` containing `chunk_data`, `chunk_index`, and `upload_id`.
- `POST /api/assemble-file`
  - Assembles previously uploaded chunks, writes the `metadata.json`, and submits the `sbatch` script to the HPC.

### **Job Polling & Results**
- `GET /api/job-status/[jobId]`
  - Polls SLURM (`squeue` / `sacct`) to check the active state of the job (e.g., `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`).
- `GET /api/job-result/[jobId]`
  - Retrieves the final data once processing is complete. Returns a unified JSON payload containing `metadata.json`, `summary.json`, and `barcode.json`.

### **Metadata Proxy**
- `GET /api/omdb/search?q={query}`
  - Proxies requests to OMDb to find movies. Caches results in-memory for 5 minutes.
- `GET /api/omdb/get?id={imdb_id}`
  - Fetches detailed movie information. Caches results in-memory for 30 minutes. 

### **Visualization**
- `GET /api/visualization/*`
  - Endpoints to assist with processing complex visualizations on the server (if they are too heavy for client-side processing), bridging logic for Hue histograms, RGB cubes, scatter plots, 3D bars, and comparisons.
